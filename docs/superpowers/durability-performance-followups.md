# Durability / WAL — Performance Follow-ups (tracked)

Deferred speed-ups we'll do **after first numbers**, each with its rationale and its
trigger (most are telemetry-gated — we measure first, then optimize the thing the data
says is the bottleneck). Kept out of the initial `--durability wal` cut to ship a
correct, measured baseline (the v1 lesson: don't pre-build the complex thing).

Branch context: `vbalegas/wal-v2`. Spec: `docs/superpowers/specs/2026-06-22-durable-wal-v2-design.md`.

| 1   | **io_uring WAL committer (`--wal-io-uring`)** ⏸️ DEFERRED (prototyped, dropped from the io_uring merge) | Collapse the WAL's per-record `pwrite` + `spawn_blocking` `fdatasync` into ~2 `io_uring_enter` calls per batch. **Prototyped** as a dedicated per-shard ring committer (was `src/wal/uring.rs`, `wal-uring` feature, `--wal-io-uring`); **removed from the branch (commit 162da343)** pending a CPU fix — design preserved in the spec + plan. **Why deferred:** the GKE A/B (10K streams, write, client_capped) showed wal+io_uring at **267.6% CPU / 0.411 %-core·kop⁻¹ vs sync wal 184.7% / 0.389** — i.e. **+37% throughput, −17 ms p99, but ~+83 CPU points (CPU/append +5.6%)**, the opposite of the strict result (#2, which was CPU-flat). **Root cause (perf review):** (1) **N per-shard committer threads busy-spin** — the process-more-first run loop never parks while the staging queue keeps refilling under load (~N spinning cores; strict uses ONE shared thread); (2) **per-record write handoff** through the ring (alloc + cross-thread queue + eventfd + inflight map + watermark-on-committer) that strict avoids (it routes only fsync). **Fix before re-landing:** bounded/timeout park on the committer instead of pure spin (biggest, lowest-risk lever — keep the proven armed+recheck lost-wakeup discipline), and/or fewer committer threads (shared ring pool), and/or fsync-only routing (keep inline `pwrite`). Design spec: `docs/superpowers/specs/2026-06-23-wal-io-uring-writes-design.md`. | After the busy-spin fix; then re-A/B server-bound vs sync wal.                                                                                      |
| 2   | **io_uring for `strict` mode** ✅ IMPLEMENTED                                                           | **Most workloads have very small payloads** → `strict`'s cost is dominated by per-append _syscalls_ (small `write` + `fdatasync`). **As built:** delivered as a single shared `UringFsync` executor (`src/uring_fsync.rs`, `strict-uring` Cargo feature, `--strict-io-uring` flag) — **not** per-stream, not a `SyncCoalescer` swap. One ring on one dedicated thread batches many streams' per-stream `fdatasync`s into ~1 `io_uring_enter` via an async oneshot bridge. On-disk format, recovery, and durability invariants unchanged. Conformance: 326/332 (identical to plain strict, 0 failures). **CPU delta pending** — rigorous A/B (server CPU% at matched append throughput, pinned cores, c1/c16/c64/c256) to be run on isolated Linux bench hardware. Design spec: `docs/superpowers/specs/2026-06-23-strict-io-uring-fsync-design.md`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | —                                                                                                                                                   |
| 3   | **Zero-copy WAL double-write**                                                                          | v1 cut buffers the payload and `write()`s it to both the per-stream file and the WAL (one user copy — cheap, but not zero-copy on the write path). Restore zero-copy via `tee`+`splice` (socket→pipe→tee→both files, kernel-to-kernel) or `copy_file_range` (WAL→per-stream file, in-kernel).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Per-op / CPU telemetry shows the buffered write-copy mattering (the `--no-fsync` data says it won't at our rates — verify). | 5   | **Dynamic shard rebalancing**                                                                           | Fixed `hash(stream_id) % N` distributes _streams_ uniformly but not _load_; a few hot streams can pile on one shard.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Per-shard batch/throughput telemetry shows sustained skew. | 6   | **"fast-WAL" variant**                                                                                  | WAL written but **not** fsync'd before ack → `fast`/relaxed speed **+** clean recovery (no torn JSON), durability via replication. Trivial given the framing already gives clean recovery.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | When a "fast but recoverable" mode is wanted (e.g., as the local layer under replication).                                                          |
| 7   | **Payload CRC (opt-in)**                                                                                | Current framing is header-CRC only (to keep `splice`); no payload bit-rot detection — same integrity as today's per-stream files.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Only if a payload-integrity requirement appears; costs a payload read (forfeits splice for crc'd records).                                          |
| 8   | **Replication (`ReplicationSink`)**                                                                     | The distributed durability backend — the "trade WAL for replication" path; quorum ack on the `fast` no-fsync write path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Separate spec; the `DurabilitySink` seam is the plug point.                                                                                         |
| 9   | **Tunable checkpoint / WAL-recycle cadence**                                                            | Trade WAL disk for checkpoint-fsync frequency: larger WAL retention ⇒ fewer (per-shard) per-stream-file fsync storms at checkpoint, more disk.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Tune from the relocated-fsync telemetry (WAL `size_bytes` vs `checkpoint_lsn` progress) per workload.                                               |

**Cross-cutting note:** items 1–3 are all "batch/avoid syscalls and copies on the
hot I/O path." Items 1 and 2 have shipped; **#3 (zero-copy WAL double-write)** is
the next syscall/copy reduction. **#2 (io_uring for strict)** shipped as the shared
`UringFsync` executor; CPU delta A/B is pending on isolated Linux bench hardware.

## io_uring v1 out-of-scope — future levers

The following items were explicitly out of scope for the initial io_uring durability work
(design spec §9). They are left here for tracking.

| #   | Follow-up                                                              | Why / notes                                                                                                                                                                                                                                                              |
| --- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1a  | **Registered fixed buffers + `IORING_REGISTER_FILES`**                 | Register WAL segment fds and per-record buffer pool with the ring → eliminate per-operation `mmap`/fd setup overhead. Only worth doing if submission overhead is still dominant after v1 measurements.                                                                   |
| 1b  | **`SQPOLL` (kernel-side submission polling)**                          | With `SQPOLL` the kernel polls the SQ, eliminating `io_uring_enter` on the submission path entirely → zero syscalls at submit time. Requires a dedicated kernel thread and elevated privilege; adds complexity for an incremental gain over v1's batched-enter approach. |
| 1c  | **io_uring for `strict`-mode per-stream fsyncs** ✅ SHIPPED as item #2 | Shipped as the shared `UringFsync` executor (`src/uring_fsync.rs`, `--strict-io-uring`); see item #2 above.                                                                                                                                                              |
| 1d  | **io_uring for checkpoint per-stream-file fsyncs**                     | Checkpoint drives one `fdatasync` per dirty stream via `spawn_blocking`; batching these into io_uring SQEs would reduce blocking-pool pressure under high-cardinality checkpoints. Low-priority: checkpoint is not on the ack path.                                      |
