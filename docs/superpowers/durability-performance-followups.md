# Durability / WAL — Performance Follow-ups (tracked)

Deferred speed-ups we'll do **after first numbers**, each with its rationale and its
trigger (most are telemetry-gated — we measure first, then optimize the thing the data
says is the bottleneck). Kept out of the initial `--durability wal` cut to ship a
correct, measured baseline (the v1 lesson: don't pre-build the complex thing).

Branch context: `vbalegas/wal-v2`. Spec: `docs/superpowers/specs/2026-06-22-durable-wal-v2-design.md`.

| #   | Follow-up                                    | Why                                                                                                                                                                                                                                                                                                                                                                                                                                           | Trigger / when                                                                                                                                                                       |
| --- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **io_uring `SegmentWriter` (WAL)**           | Collapse the WAL's per-record `write`(header)+`splice`(payload) + the batch `fdatasync` into a handful of SQEs per `io_uring_enter` — batches _all_ WAL syscalls, not just the fsync (group commit already batches that).                                                                                                                                                                                                                     | Batch telemetry shows large, fsync-amortized batches but throughput capped by per-op syscall overhead. The `SegmentWriter` abstraction is the drop-in seam (no architecture change). |
| 2   | **io_uring for `strict` mode** _(user)_      | **Most workloads have very small payloads** → `strict`'s cost is dominated by per-append _syscalls_ (small `write` + `fdatasync`). io_uring can batch the per-stream write+fsync submissions across in-flight appenders → a significant boost exactly where it hurts. Revisit the earlier io_uring server variant (won reads/fan-out; weaker append p99) **for the strict append path specifically**, with batched submission to fix the p99. | After the WAL baseline; A/B io_uring-strict vs strict on small-payload + high-cardinality cells. Likely the biggest near-term win for real small-payload workloads.                  |
| 3   | **Zero-copy WAL double-write**               | v1 cut buffers the payload and `write()`s it to both the per-stream file and the WAL (one user copy — cheap, but not zero-copy on the write path). Restore zero-copy via `tee`+`splice` (socket→pipe→tee→both files, kernel-to-kernel) or `copy_file_range` (WAL→per-stream file, in-kernel).                                                                                                                                                 | Per-op / CPU telemetry shows the buffered write-copy mattering (the `--no-fsync` data says it won't at our rates — verify). Behind `SegmentWriter`.                                  |
| 4   | **CPU pinning of committers**                | The per-CPU sharded committers are a clean place to pin each committer thread to a core (affinity → cache locality, no migration).                                                                                                                                                                                                                                                                                                            | If per-shard committer telemetry shows scheduling/cache thrash; platform-fiddly so deferred.                                                                                         |
| 5   | **Dynamic shard rebalancing**                | Fixed `hash(stream_id) % N` distributes _streams_ uniformly but not _load_; a few hot streams can pile on one shard.                                                                                                                                                                                                                                                                                                                          | Per-shard batch/throughput telemetry shows sustained skew. (Fixed allocation stays the default — rebalancing only if the data demands it.)                                           |
| 6   | **"fast-WAL" variant**                       | WAL written but **not** fsync'd before ack → `fast`/relaxed speed **+** clean recovery (no torn JSON), durability via replication. Trivial given the framing already gives clean recovery.                                                                                                                                                                                                                                                    | When a "fast but recoverable" mode is wanted (e.g., as the local layer under replication).                                                                                           |
| 7   | **Payload CRC (opt-in)**                     | Current framing is header-CRC only (to keep `splice`); no payload bit-rot detection — same integrity as today's per-stream files.                                                                                                                                                                                                                                                                                                             | Only if a payload-integrity requirement appears; costs a payload read (forfeits splice for crc'd records).                                                                           |
| 8   | **Replication (`ReplicationSink`)**          | The distributed durability backend — the "trade WAL for replication" path; quorum ack on the `fast` no-fsync write path.                                                                                                                                                                                                                                                                                                                      | Separate spec; the `DurabilitySink` seam is the plug point.                                                                                                                          |
| 9   | **Tunable checkpoint / WAL-recycle cadence** | Trade WAL disk for checkpoint-fsync frequency: larger WAL retention ⇒ fewer (per-shard) per-stream-file fsync storms at checkpoint, more disk.                                                                                                                                                                                                                                                                                                | Tune from the relocated-fsync telemetry (WAL `size_bytes` vs `checkpoint_lsn` progress) per workload.                                                                                |

**Cross-cutting note:** items 1–3 are all "batch/avoid syscalls and copies on the
hot I/O path." The single biggest expected real-world win is **#2 (io_uring for strict,
small payloads)** — strict is the default and most workloads are small-payload, so
batching its syscalls likely beats everything else for typical traffic. Prioritize #2
right after the WAL baseline numbers.
